# 合同交付文档库

本目录统一保存“轨道客室智能设计平台”后续所有合同要求文档。文档内容必须对应可追溯的代码基线，不能把路线图、占位页面、未配置适配器或历史环境验证写成当前环境已经可用的能力。

## 目录约定

每一份合同文档使用一个独立目录，目录内按以下结构管理：

```text
<文档编号>-<英文短名>/
├── README.md        # 文档身份、当前版本、代码基线与维护说明
├── source/          # 可维护源稿
├── assets/          # 图表、插图及其他受版本控制的素材
├── deliverables/    # 对外评审或交付版本（按版本号保留）
└── tools/           # 仅服务本文件的可复现生成脚本（如需要）
```

`DOCUMENT_REGISTER.md` 是全库登记表。新增、改版、作废或替换任何合同文档时，必须同步更新登记表和 `docs/rail-platform/DEVELOPMENT_LOG.md`。

## 强制版本字段

每个版本的内部源稿、文档说明或登记表至少记录以下信息：

- 文档编号、文档名称、文档版本、状态和编制日期；
- Git 分支、完整提交哈希、短提交哈希和提交时间；正式对外交付件可按甲方要求不展示代码版本和实现细节；
- 取证时工作区是否干净；若不干净，列出未提交变更是否纳入文档事实；
- 本次验证命令、结果和未验证项；
- 与上一版相比的主要变化及仍存在的外部依赖。

代码基线指“本版文档所描述系统的提交”，不包含为了编制该文档而新增的源稿、成品和登记记录。文档改版时不得只修改版本号；应重新核对实际代码、迁移、配置、测试和运行证据。

## 版本与归档规则

1. 初版使用 `V1.0`；内容补充但结论不变时递增次版本，系统边界或核心结论变化时递增主版本。
2. `source/` 和 `deliverables/` 的文件名必须含版本号。旧版本保留，不覆盖，登记表仅将一个版本标记为“当前”。
3. 图片、流程图和表格必须能回溯到同版源稿；不得引用仓库外的临时文件作为唯一依据。
4. 对外发布前至少完成内容复核、敏感信息检查、DOCX 逐页渲染检查和链接/文件完整性检查。
5. 合同编号、委托单位、承担单位、作者或审批人未提供时统一标为“待项目组补充”，不得自行编造。
6. 含联系人、电话、邮箱、地址、银行账户、金额或印章等敏感信息的合同原件不复制进仓库；仓库只保存合同文件名、校验哈希及脱敏后的技术要求矩阵。
