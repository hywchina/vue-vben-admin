# ComfyUI 工作流 API 接入任务规划

> 文档状态：待执行  
> 前置条件：核心模块重构完成  
> 适用范围：ComfyUI API 工作流接入 `项目 - 资产 - 任务 - AI/外部能力插件化平台`  
> 输入分支：主平台 `refactor-core-module` 输出分支：主平台 `refactor-webUI` 参考资料（只读，不改动）：
>
> - `<外部 ComfyUI 仓库>`
> - `<外部 ComfyUI 仓库>/webUI` 实施范围：仅修改 本仓库 项目，不修改原始 `ComfyUI` 项目

## 1. 任务背景

ComfyUI 是独立于主平台之外的工作流编排与执行系统。它支持在页面中编辑工作流，并可将工作流导出为可调用的 API JSON。当前已经存在一个专门的 `webUI` 验证项目，用来自动扫描 `workflows_api/*.json`，为每个工作流生成一个简单参数页面，并直接调用 ComfyUI 的 API 来验证：

- 工作流能否执行
- 参数能否在 Web 端展示和设置
- 上传、轮询、结果查看是否可用

这套 `webUI` 的定位是“工作流 API 验证台”，不是最终业务平台。现在要做的是，把这类 API 工作流正式接入主平台，使其成为主平台“应用 - 任务 - 资产”体系中的外部能力。

本任务的实施对象只有 本仓库。`<外部 ComfyUI 仓库>` 及其 `webUI` 仅作为静态分析、交互参考和模拟测试参考来源，不在本轮改造范围内。

## 2. 核心目标

本任务的目标不是把 ComfyUI 画布搬进主平台，而是把“已经调试通过、可导出的 API 工作流”纳入主平台统一能力体系。

最终需要做到：

1. 主平台能够以外部能力适配器的方式调用 ComfyUI API 工作流。
2. 用户在主平台中发起工作流任务，任务进入平台任务台账，而不是停留在 ComfyUI 独立控制台中。
3. 工作流输出的图片等结果能够登记为平台资产。
4. API 调用能力对用户开放，但输出资产必须按平台用户与项目范围归属。
5. 当前接入方案支持先落单个工作流 API，后续再演进为“文生图、图生图、局部重绘”等面向业务的能力视图。

## 3. 已确认的前提与约束

### 3.1 前提

- 本任务建立在“核心模块重构完成”之后。
- 主平台已预留任务型外部适配器边界，当前默认返回 `ADAPTER_NOT_CONFIGURED`。
- 主平台已有应用目录、任务台账、资产登记、对象存储、审计与项目隔离体系。
- 本任务从主项目 `refactor-core-module` 分支继续推进，输出到 `refactor-webUI` 分支。

### 3.2 已知限制

- 当前本地 ComfyUI 服务无法稳定启动，因此本轮不能依赖真实本地联调。
- 当前阶段以静态分析、架构设计、模拟测试方案和任务规划为主。
- 参考实现主要来自 `ComfyUI/webUI`，不是直接复用整个前端页面。
- 原始 `ComfyUI` 项目及其 `webUI` 不做任何代码修改。
- 当前保存在 `ComfyUI` 项目内的 API JSON，后期需要迁移到主平台可管理体系中，由主平台管理员进行配置和维护。

### 3.3 关键业务约束

- API 能力面向所有有权限的用户开放。
- 工作流输出资产必须属于发起任务的用户，并落在当前业务上下文中。
- 如果主平台要求项目隔离，则工作流结果必须同时具备项目归属和用户归属。
- 浏览器不应直接持有 ComfyUI 的地址、密钥或管理能力。
- ComfyUI 的成功执行不能自动等价于平台任务完成，只有当结果被平台接收、校验并登记为资产后，平台任务才算完成。
- 长期目标是让 本仓库 成为独立项目，工作流配置、管理入口和业务接入能力都在主平台内部闭环，不再依赖 `ComfyUI` 仓库提供配置文件。

## 4. 现状调研结论

## 4.1 ComfyUI `webUI` 的真实定位

`<外部 ComfyUI 仓库>/webUI` 当前是一个验证型控制台，不是生产业务前端。它的核心能力包括：

- 自动扫描 `user/default/workflows_api/` 下的工作流 JSON
- 通过 `/object_info` 自动识别可编辑输入
- 根据 API 工作流生成参数表单
- 调用 `/prompt` 提交任务
- 轮询 `/history/{prompt_id}` 和 `/queue`
- 使用 `/view` 查看结果，使用 `/upload/image` 上传输入图片

它适合作为以下内容的参考来源：

- API 工作流的结构约束
- 参数提取逻辑
- 特殊输入处理方式
- ComfyUI 最小执行链路
- 结果轮询与错误处理方式

但它不适合作为主平台的直接实现方案，因为：

- 它没有主平台的用户、项目、资产、任务、审计和权限边界
- 它直接面向工作流文件和 ComfyUI 代理，不是面向业务能力
- 它关注“每个工作流一个简易参数页”，不是面向最终产品用户的业务体验

同时还需要强调：`webUI` 是参考样板，不是代码迁移目标。本轮不能以修改 `webUI` 的方式完成平台接入，而应在主平台内重建相应能力。

## 4.2 `webUI` 当前验证的关键技术事实

根据 `webUI/README.md`、`DEVELOPMENT.md`、`server.py` 和 `app.js`，可以确认：

1. API 工作流目录是 `user/default/workflows_api/`
2. API JSON 是以节点 ID 为键的执行图，不是画布 JSON
3. 未连接的字面量输入可被抽取为可编辑参数
4. 图片类输入通过 `/upload/image` 先上传，再把文件名写回对应节点输入
5. 执行入口为 `POST /prompt`
6. 结果通过 `GET /history/{prompt_id}` 查询
7. 文件输出通过 `GET /view` 查看
8. `webUI` 已经证明“单个工作流 API 可以自动生成简易参数页并成功执行”

这说明主平台后续接入时，并不需要重新发明工作流执行协议，重点是要把这条能力链路纳入平台业务模型。

## 4.3 主平台当前可承接的能力基础

主平台当前已具备以下承接能力：

- `applications`：应用目录，可描述输入/输出资产契约
- `jobs`：任务台账
- `job_inputs` / `job_outputs`：任务输入输出关联
- `assets`：资产登记、预览、下载与归属
- 对象存储：用于保存大文件输出
- 审计日志：记录任务提交、结果落库、失败原因
- `workspace/:appKey`：动态应用工作区

架构文档已经明确：ComfyUI 这类外部能力应通过平台适配器接入，而不是让浏览器直接访问第三方执行服务。

## 5. 总体接入思路

本任务建议分为两步推进。

## 第一步：先接入主平台，跑通单个工作流 API

目标是先解决“平台可调用、任务可追踪、结果可沉淀”的闭环问题。

这一阶段强调：

- 单个工作流 API 可以从主平台成功发起
- 任务能进入主平台任务台账
- 结果能成为平台资产
- 用户归属、项目归属、审计与失败路径清晰
- 不依赖改动原始 `ComfyUI` 项目
- 在当前本地服务不可用条件下，能够通过 `webUI` 结构参考和模拟数据验证主平台接入设计

这一阶段不追求把工作流包装成高度产品化的业务页面，也不追求统一抽象所有工作流。

## 第二步：预留后期迭代优化空间

目标是把“每个工作流一个参数页”的验证模式，演进为面向业务用户的能力中心。

这一阶段强调：

- 用户侧看到的是“文生图、图生图、局部重绘、扩图、多视图”等能力分类
- 前端不直接暴露复杂节点参数
- 前端根据所选能力和场景自动映射到具体工作流 API
- 工作流能力逐步从“技术工作流”升级为“产品化能力”
- 工作流 JSON 配置由主平台管理员维护，而不是继续放在外部仓库中手工管理

## 6. 第一阶段详细规划：先接入主平台并跑通单个工作流 API

## 6.1 阶段目标

完成一个最小可交付闭环：

1. 主平台新增一个 ComfyUI 工作流型应用
2. 用户可在平台工作区中发起任务
3. 平台后端适配器调用 ComfyUI 工作流 API
4. 平台可轮询或接收任务结果
5. 生成图片等输出被写入对象存储并登记为资产
6. `job_outputs` 建立任务与输出资产关系
7. 用户可在任务中心、资产中心中看到结果

## 6.2 第一阶段建议交付边界

建议只选 1 个最典型、最稳定、输入输出最清晰的工作流作为样板接入，例如：

- 文生图或
- 单图编辑/图生图

建议优先文生图，因为：

- 输入简单
- 对资产输入依赖最少
- 易于先验证任务链路和输出资产登记

本阶段只改主平台，不复制、不改写原始 `ComfyUI` 工程代码。若需要样板工作流配置，可在主平台中建立独立的工作流注册/配置目录，基于现有 API JSON 做受控引入。

## 6.3 第一阶段架构设计

### 前端侧

- 在 `applications` 中新增对应的 ComfyUI 应用定义
- 在 `/workspace/:appKey` 工作区内提供该工作流的参数表单
- 第一阶段允许页面参数较“技术化”，但必须在主平台统一外壳内运行
- 表单提交后调用主平台 `/jobs` 或专用工作流任务接口，而不是直接请求 ComfyUI
- 相关页面、表单、状态与配置均在 本仓库 项目内部实现

### 平台 API 侧

- 在任务执行链路中新增 ComfyUI 适配器
- 根据应用定义和工作流配置，构造 ComfyUI `/prompt` 请求
- 对输入图片类参数执行必要的对象准备或上传流程
- 保存第三方任务标识，例如 `prompt_id`
- 轮询 `/history/{prompt_id}` 或设计后续异步更新机制
- 成功后拉取输出文件并接入平台对象存储
- 创建平台资产并写入 `job_outputs`

### 外部能力侧

- ComfyUI 仅负责工作流执行
- 工作流 JSON 作为受控配置，不应让前端直接读取本地文件系统
- 平台侧需要有工作流清单、工作流版本、参数映射和输出约束的管理方式
- 原始 `ComfyUI` 仓库只作为参考资料来源，不参与本轮代码变更

## 6.4 第一阶段数据链路

建议数据流如下：

1. 用户在主平台进入某个 ComfyUI 应用工作区
2. 选择项目上下文，填写参数或选择输入资产
3. 主平台创建任务记录，状态为 `queued` 或 `running`
4. 平台后端根据预设工作流模板构造 API JSON
5. 平台后端调用 ComfyUI `/prompt`
6. 平台保存 `prompt_id`、工作流标识、参数快照和任务元数据
7. 平台轮询 ComfyUI 结果
8. 平台下载输出文件并写入 MinIO/S3
9. 平台登记输出资产，资产来源标记为对应应用/任务
10. 平台更新任务状态为 `completed` 或 `failed`
11. 用户在任务中心、资产中心、应用工作区查看结果

## 6.5 第一阶段参数处理策略

第一阶段不建议直接照搬 `webUI` 的“扫描所有未连接节点并动态生表单”方式进入主平台主界面，而建议采用：

- 主平台维护“受控工作流配置”
- 每个接入的工作流明确列出允许暴露给用户的参数
- 平台把业务表单字段映射到工作流 JSON 的具体节点输入

原因：

- 平台是产品，不是工作流调试台
- 动态暴露全部参数会把节点级复杂性直接暴露给终端用户
- 受控映射更利于审计、回归和后续产品化

但 `webUI` 的参数识别逻辑仍然有价值，可作为平台内部“工作流接入辅助工具”的参考。

## 6.5.1 工作流配置管理与管理员入口

为保证主平台长期独立运行，第一阶段就应预留工作流配置内置化能力。

建议后续由主平台管理员完成以下操作：

- 新增工作流配置
- 上传或粘贴 API JSON
- 配置工作流名称、编码、分类、版本和状态
- 配置参数白名单、默认值、输入输出类型
- 启用/停用某个工作流

第一阶段可以先不做完整管理后台 UI，但至少在设计上明确：

- 工作流配置最终归属于主平台自身
- 不再依赖 `ComfyUI` 项目目录中的 JSON 作为长期运行时配置源
- 后续管理员能够在主平台内维护这些配置

## 6.6 第一阶段资产归属与范围控制

这是本阶段最关键的业务设计点。

### 必须满足

- 任务的创建者是当前用户
- 输出资产的 `owner` 必须是当前用户
- 输出资产必须关联当前项目
- 资产来源必须能追溯到对应 `job`、`application`、`workflow`

### 推荐实现

- 任务表中记录 `created_by`
- 资产表中记录 `owner_id`、`project_id`、`source_app_key`、`source_job_id`
- 输出资产统一走平台资产登记流程，而不是直接使用 ComfyUI 输出目录
- 如需保留原始输出文件名，可作为资产元数据保存

### 需要明确的边界

- API 调用能力可以对所有有权限用户开放，不等于用户之间共享输出资产
- 不允许用户通过猜测任务 ID 或第三方输出地址访问他人结果
- 不允许浏览器直接使用 ComfyUI `/view` 地址作为长期结果 URL

## 6.7 第一阶段任务状态设计

建议平台任务状态至少包括：

- `queued`
- `running`
- `completed`
- `failed`
- `cancelled`

建议额外保存：

- 第三方任务 ID：`prompt_id`
- 第三方服务标识：`comfyui`
- 工作流标识与版本
- 关键输入参数摘要
- 失败错误码与失败原因

如果 ComfyUI 未配置或工作流未注册，仍应保持当前平台规范，返回稳定错误而不是伪成功。

## 6.8 第一阶段审计要求

至少记录以下事件：

- 用户发起 ComfyUI 任务
- 平台调用外部工作流服务
- 外部服务返回任务 ID
- 平台完成输出资产登记
- 任务失败、取消或超时

日志中不记录：

- 敏感密钥
- 完整二进制内容
- 不必要的原始大字段

## 6.9 第一阶段建议交付物

- 1 个已接入的 ComfyUI 工作流应用
- 1 条完整任务执行链路
- 任务中心可见的任务记录
- 资产中心可见的输出资产
- 可追溯的工作流配置文件或注册清单
- 对应测试与交付文档

## 7. 第二阶段详细规划：演进为面向业务用户的能力层

## 7.1 阶段目标

在第一阶段“单工作流接入成功”的基础上，进一步把 ComfyUI 能力产品化。

用户最终不应只看到一堆工作流文件名，而应看到更符合业务理解的能力入口，例如：

- 文生图
- 图生图
- 局部重绘
- 扩图
- 多视图生成
- 图片理解

## 7.2 第二阶段核心思路

建立“能力层 -> 工作流层”的映射关系：

- 用户面向能力操作
- 前端根据用户所选模式与参数，自动匹配对应工作流
- 平台后端根据能力配置生成最终的工作流调用请求

也就是说：

- 用户操作的是产品化能力模型
- 平台调度的是底层工作流模型

## 7.3 第二阶段前端形态

前端建议从“每个工作流一个简易参数页”演进为：

- 能力分类页
- 统一风格的输入面板
- 业务术语参数，不直接暴露节点术语
- 能力模板、预设、快捷选项
- 高级参数折叠或按权限开放

例如文生图页面可只暴露：

- 正向提示词
- 负向提示词
- 尺寸
- 风格/模型
- 生成数量
- 随机种子或是否随机

而不直接暴露原始节点层的全部输入字段。

## 7.4 第二阶段后端形态

后端建议新增能力配置层，描述：

- 能力编码
- 底层工作流 ID
- 工作流版本
- 输入映射规则
- 默认参数
- 可选参数范围
- 输出类型
- 是否需要输入资产

这样后续即使更换工作流版本，也可不影响前端能力入口。

## 7.5 第二阶段多工作流管理策略

后续工作流会越来越多，建议从第二阶段开始建立如下机制：

- 工作流注册表
- 工作流版本管理
- 工作流启用/停用状态
- 能力与工作流的映射表
- 工作流参数白名单
- 输出资产类型与后处理规则

避免把工作流文件名直接当产品能力主标识。

## 7.6 第二阶段与平台资产体系的进一步融合

后续不只是“结果落资产”，还要逐步支持：

- 选择现有资产作为工作流输入
- 输出资产自动携带标签、来源和血缘
- 同一项目内结果可被后续能力复用
- 形成“输入资产 -> 任务 -> 输出资产 -> 下游任务”的连续链路

## 8. 工作流接入的推荐抽象层次

建议后续把 ComfyUI 接入拆成四层：

### 8.1 工作流原始层

- 来自 ComfyUI 导出的 API JSON
- 保留原始结构
- 用于溯源与问题排查

### 8.2 工作流注册层

- 描述工作流 ID、版本、分类、状态
- 记录输入输出契约
- 记录允许暴露的参数

### 8.3 能力映射层

- 将业务能力映射到一个或多个工作流
- 管理参数转换、默认值和版本切换

### 8.4 平台执行层

- 负责任务创建、外部调用、状态更新、输出落资产、审计与错误处理

这样可以把“工作流文件本身”和“平台业务能力”解耦开。

## 9. 配置与接口规划建议

## 9.1 平台环境变量建议

后续建议为平台 API 配置独立的 ComfyUI 适配器环境变量，例如：

```dotenv
COMFYUI_API_URL=https://comfy.internal.example
COMFYUI_API_TIMEOUT_MS=60000
COMFYUI_API_TOKEN=<由部署平台注入，如后续需要>
COMFYUI_WORKFLOW_REGISTRY_PATH=...
COMFYUI_OUTPUT_BUCKET_PREFIX=comfyui
```

具体名称以后续实现为准，但原则不变：

- 第三方地址和凭据只保留在服务端
- 不泄露给浏览器
- 不写死在前端配置中

## 9.2 平台内部接口建议

主平台后续可能需要以下内部能力接口：

- 获取可用 ComfyUI 应用/能力列表
- 获取某能力的表单配置
- 创建 ComfyUI 任务
- 查询 ComfyUI 任务状态
- 取消 ComfyUI 任务
- 查询该任务产出的资产
- 管理员新增/更新/停用工作流配置
- 管理员查看工作流版本与启用状态

如果继续沿用当前 `/jobs` 统一入口，也应在参数结构中明确区分：

- 应用标识
- 工作流标识
- 业务参数
- 输入资产列表

## 11. 风险与关键决策点

| 风险/决策点 | 说明 | 规划建议 |
| --- | --- | --- |
| 直接暴露所有工作流参数 | 会把节点复杂性直接暴露给业务用户 | 第一阶段受控暴露，第二阶段能力化封装 |
| 直接让浏览器调用 ComfyUI | 会破坏平台边界和安全模型 | 必须通过平台 API 适配器调用 |
| 输出只停留在 ComfyUI 目录 | 无法纳入平台资产体系 | 结果必须进入平台对象存储和资产登记流程 |
| 只记录第三方任务成功 | 平台侧可能尚未完成资产登记 | 平台任务完成必须以“结果已接收并登记”为准 |
| 工作流文件名即产品能力名 | 后续版本切换与产品化会混乱 | 建立能力层与工作流层映射 |
| 长期依赖外部仓库中的 JSON | 主平台无法独立交付与运维 | 将工作流配置迁移到主平台管理员可维护体系 |
| 当前本地服务无法启动 | 难以直接做真实联调 | 当前阶段先用 `webUI` 参考和模拟数据测试，后续再补真实联调 |
| 用户可调用 API 能力 | 不代表结果共享 | 结果资产仍严格按用户/项目归属控制 |

## 12. 实施顺序建议

1. 完成核心模块重构

7. 完成第一阶段测试和交付
8. 再进入能力化抽象和第二阶段产品化演进

## 13. 第一阶段完成判定

满足以下条件后，可认为第一阶段完成：

1. 主平台中至少 1 个 ComfyUI 工作流应用可用
2. 用户可在主平台中发起并追踪该任务
3. 任务结果可登记为平台资产
4. 资产具备用户归属、项目归属和任务来源
5. 失败路径、取消路径和审计路径清晰
6. 自动化测试和基本浏览器验证通过

## 14. 第二阶段完成判定

满足以下条件后，可认为第二阶段完成：

1. 用户侧能力入口不再直接暴露工作流文件名
2. 至少一类能力完成“能力层 -> 工作流层”映射
3. 参数展示已面向业务术语，而不是节点术语
4. 工作流版本切换不需要重做前端页面
5. 多工作流接入具备统一注册和管理机制
