# 核心模块重构计划安排

> 文档状态：执行中  
> 目标分支：`refactor-core-module`  
> 输入分支：`dev`  
> 适用范围：`项目 - 资产 - 任务 - AI/外部能力插件化平台` 相关核心模块  
> 本文用途：作为本轮彻底重构的执行依据、交付依据与上线前核查依据

## 1. 背景与目标

当前仓库最初来自 `vue-vben-admin`，后续已经完成面向“轨道交通客室智能设计平台”的二次开发，形成了以项目为边界、以资产为核心、以任务为链路、以 AI/外部能力为插件的统一设计平台。

但仓库内部仍残留大量原始模板的结构、页面、依赖习惯、命名痕迹和历史实现路径。这些内容已经不能有效服务当前业务平台，反而会带来以下问题：

- 核心业务模块边界不清晰，业务实现与模板遗留能力混杂。
- 新成员接手时难以快速识别“哪些是平台真需求，哪些是模板残留”。
- 后续接入同类型组件、更多外部能力或多版本变体时，容易重复开发和重复重构。
- 测试、交付、上线时很难明确哪些模块是必须保留的产品能力，哪些模块只是历史包袱。

因此，本轮工作不是局部修补，而是一次围绕核心平台能力的系统性重构，目标是：

1. 让仓库结构、模块组织和依赖关系真正服务当前业务平台。
2. 明确隔离原始模板遗留内容与二次开发核心能力。
3. 为后续同类组件、多版本变体和外部能力接入预留清晰扩展点。
4. 将重构过程纳入可追溯的 Git 基线与分步提交体系。
5. 通过完整测试矩阵和上线门禁，确保重构后仍是可交付、可上线的产品。

## 2. 重构范围

本次重构聚焦以下核心平台能力：

- 用户认证与会话
- 平台角色与权限控制
- 项目上下文与项目范围隔离
- 资产中心与资产类型约束
- 应用目录与应用工作区
- 任务台账与输入输出资产链路
- AI 助手与外部能力接入边界
- 操作日志、通知、个人资料等平台基础能力
- 与上述能力直接耦合的前端页面、状态管理、API、迁移、脚本、测试与部署配置

本次重构不以“新增业务功能”为目标，但允许为了实现重构目标而进行以下必要调整：

- 目录重组
- 公共逻辑抽取
- 基类/工具层收敛
- 依赖清理或替换
- 测试补齐
- 文档补齐
- 构建、脚本、CI、部署入口的必要对齐

## 3. 不在本轮目标内

以下内容默认不作为本轮主要交付目标，除非它们直接阻塞核心模块重构：

- 新增全新业务域功能
- 引入新的第三方 AI/工作流执行器
- 大规模视觉改版
- 与当前平台目标无关的原始模板功能增强
- 无需求支撑的性能优化或技术栈替换
- 为追求整洁而进行的大范围历史代码“顺手清理”

原则上坚持“围绕核心目标的最小必要改动”，避免把重构演变成不可控的全面翻新。

## 4. 执行原则

### 4.1 任务基线与溯源原则

本轮重构采用“原始基线 + 分步人工改造”的方式推进：

1. 先识别待纳入本轮重构路径的原始代码、资源、脚本和配置。
2. 将待引入内容完整、无修改复制至目标目录。
3. 形成第一次基线提交，用于界定“原始引入内容”。
4. 所有后续变更均基于该基线开展，确保人工改动与原始内容可区分、可追溯、可回滚。

该原则适用于代码、静态资源、配置文件、测试文件、脚本文件和文档文件。

### 4.2 架构扩展性原则

在重构当前核心模块时，必须同步考虑未来的复用与扩展：

- 同类页面和同类工作区的目录组织是否可复用。
- 多个应用/能力接入时，输入输出契约是否可复用。
- 多版本变体并存时，公共逻辑和变体逻辑是否可隔离。
- 前端状态、后端服务、测试夹具、脚本工具是否可以沉淀为公共层。
- 是否已经为后续外部能力接入预留稳定边界，而不是直接写死在现有模块里。

### 4.3 工程规范原则

- 所有新增与修改内容必须对齐仓库现有工程规范。
- 命名、路径、导出方式、脚本命令、配置风格保持一致。
- 不引入无必要的风格切换和范式切换。
- 优先复用已有工具、脚本、测试设施和构建链路。

### 4.4 产品可交付原则

重构完成的标准不是“代码看起来更整洁”，而是：

- 核心业务仍然完整可运行。
- 权限、数据隔离、审计和对象存储边界没有退化。
- 自动化测试与手工验收可证明重构后的产品仍可交付。
- 部署、回归、故障定位和上线流程可以复现。

## 5. 分支与 Git 管理方案

### 5.1 分支策略

- 输入分支：`dev`
- 重构分支：`refactor-core-module`
- 所有本轮改动仅落在 `refactor-core-module`
- 未经确认，不在本轮顺带处理 `dev` 上无关问题

### 5.2 提交拆分规则

每条提交只完成一个独立目标，建议按如下粒度拆分：

1. 基线引入
2. 目录与模块边界调整
3. 公共逻辑抽取
4. 单个子模块重构
5. 测试补齐
6. 构建/部署/CI 对齐
7. 文档与交付材料补齐

禁止把多个不相关改动混成一个超大提交。

### 5.3 Commit Message 规则

- 统一使用英文
- 推荐使用 Conventional Commit 风格
- 示例：
  - `refactor(platform): reorganize core module directories`
  - `test(platform): add integration coverage for asset workflows`
  - `docs(project): add core module refactor plan`

### 5.4 Commitlog 管理规则

重构过程中维护独立的 `commitlog` 文件，逐条记录：

- 提交哈希
- 英文 commit message
- 中文变更动机
- 中文改动范围
- 影响模块
- 风险与注意事项
- 是否涉及迁移、部署、测试补充

建议文件名：`docs/rail-platform/REFACTOR_COMMITLOG.md`

## 6. 重构总体阶段安排

## 阶段 0：准备与基线确认

### 目标

- 明确本轮核心模块边界
- 明确保留、迁移、隔离、待删、待观察内容
- 固化重构计划、提交流程和测试门禁

### 主要工作

- 盘点当前仓库目录，识别原始模板残留路径和平台真实运行路径。
- 梳理 `apps/web-antd`、`apps/platform-api`、`packages`、`internal`、`scripts`、`deploy` 的职责边界。
- 标注当前核心运行链路涉及的页面、API、迁移、脚本和测试入口。
- 建立重构范围清单、风险清单和回归清单。

### 交付物

- 本文档
- 核心模块范围清单
- 风险与依赖清单
- 初版回归清单

## 阶段 1：原始基线引入与首次提交

### 目标

- 完整保留待引入的原始代码/资源基线
- 为后续人工重构提供清晰的对照面

### 主要工作

- 将待引入的原始模块、资源、脚本、测试或配置完整复制至目标位置。
- 严格禁止在该步骤中混入重构逻辑、命名调整或代码修正。
- 完成首次 baseline commit。

### 交付物

- 基线目录
- 基线提交记录
- commitlog 对应说明

## 阶段 2：核心目录与模块边界重构

### 目标

- 让仓库结构直接映射当前平台领域模型
- 降低原始模板结构对核心模块理解和维护的干扰

### 主要工作

- 重新审视核心模块目录组织，按平台领域而非模板来源组织代码。
- 收敛前端页面、状态、接口定义、常量、类型、工具的归属。
- 收敛后端 API、服务、校验、数据访问、对象存储、审计的边界。
- 识别仅为模板服务、与平台目标无关的壳层内容并隔离。

### 验收标准

- 新成员可以快速区分核心平台代码与历史残留代码。
- 单个业务模块的页面、状态、接口、类型和测试能在有限路径内定位。
- 后续新增同类模块时可沿用同一目录约定。

## 阶段 3：公共层抽象与扩展接口预留

### 目标

- 抽取稳定公共逻辑
- 为同类模块、多版本变体、外部能力扩展提供复用基础

### 主要工作

- 抽取通用表单、上传、鉴权、项目上下文、资产契约、任务状态、AI 调用边界等公共逻辑。
- 识别适合沉淀为基类、组合函数、工具函数、脚本模板和测试夹具的部分。
- 预留组件变体接口、适配器接口、能力注册接口或扩展点。
- 避免直接面向单个页面或单个能力写死逻辑。

### 验收标准

- 公共逻辑位置明确，重复实现显著下降。
- 新增同类型能力时，能在不大改现有目录的前提下接入。
- 外部能力未配置时仍保持稳定失败而不是伪成功。

## 阶段 4：核心子模块逐项重构

### 目标

- 逐个子模块去除原始模板痕迹
- 保持核心业务能力持续可运行

### 建议子模块顺序

1. 认证与用户会话
2. 角色权限与路由访问控制
3. 项目上下文与项目隔离
4. 资产中心与资产类型契约
5. 应用目录与应用工作区
6. 任务台账与任务状态流转
7. AI 助手与附件链路
8. 审计日志、通知与个人资料

### 每个子模块的标准动作

- 明确输入输出边界
- 清理模板遗留依赖
- 对齐当前平台命名和职责
- 补齐必要测试
- 完成独立提交与 commitlog 记录

## 阶段 5：测试补齐与质量固化

### 目标

- 让重构结果不依赖“人工感觉没问题”
- 建立完整测试分层和上线前证据链

### 主要工作

- 按模块补齐单元测试和状态测试。
- 按关键业务链路补齐 API 集成测试。
- 补齐浏览器冒烟与关键路径验收。
- 对迁移、对象存储、权限隔离、AI 会话隔离等高风险点建立强制验证项。
- 将测试要求固化进 CI 和发布前清单。

## 阶段 6：部署、交付与上线准备

### 目标

- 确保重构后不是“仅能本地跑”的代码，而是可交接、可部署、可上线的产品版本

### 主要工作

- 校对开发、测试、生产部署文档。
- 校对环境变量、Docker、Compose、Nginx、迁移和启动顺序。
- 检查生产配置占位符、安全项、就绪探针和备份恢复说明。
- 准备上线前验证记录与回滚预案。

### 交付物

- 通过测试与构建的重构分支
- 完整 commitlog
- 交付说明
- 发布前检查清单
- 已验证的部署与回滚说明

## 7. 目录与架构重构关注点

本轮重构至少应重点检查以下问题：

### 7.1 前端层

- `apps/web-antd/src/views` 中哪些页面仍带有模板示例性质
- `modules`、`store`、`router`、`api`、`components` 是否围绕平台领域组织
- 是否仍存在静态假数据、仅内存演示状态、与平台目标无关的 UI 示例依赖
- 权限控制是否分散在多个不一致入口
- 应用工作区是否具备后续多能力扩展的统一容器结构

### 7.2 后端层

- 认证、权限、项目范围、资产、任务、AI 助手、审计是否仍有模板式路径或薄弱边界
- 文件式 API 目录是否能清晰映射平台领域
- 共享校验、错误码、响应封装、事务、对象存储控制是否足够收敛
- 外部能力适配器边界是否稳定，是否避免直接侵入核心平台领域

### 7.3 数据与脚本层

- 迁移命名与顺序是否清晰
- 种子脚本、重建脚本、集成脚本是否仍带有临时性或演示性痕迹
- 对象存储、预签名、附件清理、失败补偿是否有统一入口

### 7.4 部署与工程基础设施

- `deploy/rail-platform` 是否已与当前平台目标完全一致
- CI 是否覆盖真正高风险能力，而非只覆盖模板基础能力
- 构建产物、环境模板、健康检查、备份恢复说明是否可直接用于交接

## 8. 测试与质量保障方案

本轮重构必须建立“开发中持续验证 + 子模块完成验证 + 分支交付前全量验证”的测试体系。

## 8.1 测试总原则

- 每一轮重构都必须有可证明的回归验证。
- 优先补高风险能力的测试，而不是追求形式化覆盖率。
- 自动化测试优先覆盖权限、隔离、持久化、对象存储、任务链路和 AI 会话等关键风险点。
- 手工测试必须服务于用户视角、部署视角和上线视角。

## 8.2 冒烟测试

### 目标

快速确认核心产品链路未被重构破坏，适合每日开发后、每个阶段完成后、提测前执行。

### 执行方式

- 本地启动完整开发环境
- 通过真实浏览器执行最短关键路径
- 重点观察页面可达性、接口成功率和控制台报错

### 冒烟测试建议清单

1. 用户名密码登录成功，进入平台首页。
2. 顶栏当前用户、项目切换、通知入口可用。
3. 项目列表可加载，切换项目后页面状态正确刷新。
4. 资产列表可加载，文本资产和文件资产至少能完成一种创建。
5. 图片类资产可预览，文件类资产可下载。
6. 应用中心和应用工作区可打开，无路由错误。
7. 任务中心可查看既有任务记录，状态展示正常。
8. AI 助手弹窗可打开，对话列表可加载，发送消息后结果明确。
9. 操作日志页面可打开，普通用户只能看到自己的日志。
10. 浏览器控制台无新增致命错误。

### 通过标准

- 所有核心入口可达
- 无白屏、无致命报错、无明显数据串读
- 关键接口返回与页面状态一致

## 8.3 单元测试

### 目标

验证纯函数、边界校验、状态计算和小范围逻辑，降低重构时局部逻辑退化的风险。

### 优先覆盖对象

- 权限判断与角色限制
- 项目范围判断
- 资产类型、MIME、扩展名校验
- AI 外部响应解析
- 错误码映射
- 审计元数据生成
- 表单转换与状态计算
- 任务状态衍生逻辑

### 通过标准

- 新增或调整的核心纯逻辑必须有对应测试
- 已有单元测试不得因重构无故删除
- 失败路径和边界条件必须覆盖，而不是只测 happy path

## 8.4 状态测试

### 目标

验证前端 store、组合逻辑和模块状态流转，避免重构后出现页面能打开但状态错乱的问题。

### 重点覆盖对象

- 当前项目切换与缓存同步
- 用户角色变化后的前端状态刷新
- 资产创建后的列表回写或刷新策略
- AI 对话切换、消息追加、清空后的状态恢复
- 管理页筛选条件与分页状态同步

## 8.5 集成测试

### 目标

验证真实 API、数据库、对象存储和关键业务链路，确保重构没有破坏跨层协作。

### 重点覆盖对象

- 认证、刷新、退出登录
- 企业邮箱密码重置
- 项目隔离与资源范围校验
- 资产上传、完成登记、预览、下载
- 任务创建、查询、输出关联
- AI 会话、附件上传、清空、跨用户隔离
- 操作日志范围控制
- 管理员角色修改和末位管理员保护

### 通过标准

- 所有高风险链路至少保留一条真实集成用例
- 使用唯一测试数据，不污染现有开发数据
- 失败场景要验证错误码和数据清理/补偿结果

## 8.6 端到端/浏览器测试

### 目标

站在真实用户视角验证页面交互、表单、弹窗、路由和上传体验。

### 建议优先固化为自动化的场景

1. 登录 / 退出登录
2. 忘记密码 / 重置密码
3. 创建项目并切换当前项目
4. 创建文本资产
5. 上传图片并预览
6. 打开应用工作区并筛选兼容资产
7. 打开 AI 助手、发送消息、上传附件、清空对话
8. 管理员修改其他用户角色
9. 普通用户访问受限页面被拦截
10. 普通用户日志范围只包含本人

### 重点检查

- 控件可用性
- 表单校验文案
- 弹窗与抽屉交互
- 上传进度与失败反馈
- 响应式和窄屏可用性
- 控制台报错与网络请求异常

## 8.7 非功能测试

### 目标

确保系统不仅功能正确，还满足上线要求。

### 应包含内容

- 构建测试：`pnpm build:rail`
- 规范检查：`pnpm lint`
- 类型检查：`pnpm typecheck:rail`
- 依赖启动与健康检查验证
- 备份与恢复演练
- 对象存储不可用时的 ready 行为验证
- SMTP/AI 外部服务未配置时的失败路径验证
- 基本性能与稳定性检查
- 生产配置安全检查

### 建议性能关注点

- 非上传 API 在常规负载下响应稳定
- 列表分页在目标规模下不出现无界查询
- 上传与预览不阻塞主链路
- AI 助手失败或超时不会拖垮主界面

## 8.8 回归测试矩阵

| 测试层级     | 执行时机               | 覆盖重点           | 是否必须 |
| ------------ | ---------------------- | ------------------ | -------- |
| 冒烟测试     | 每日开发后、阶段完成后 | 核心入口与主链路   | 是       |
| 单元测试     | 每次局部重构后         | 纯逻辑与边界条件   | 是       |
| 状态测试     | 前端状态改动后         | store 与状态流转   | 是       |
| 集成测试     | 涉及 API/DB/S3/权限时  | 跨层链路与隔离     | 是       |
| 浏览器验收   | UI 和交互改动后        | 真实用户流程       | 是       |
| 构建测试     | 每阶段结束、提测前     | 可部署产物         | 是       |
| 部署验证     | 提交交付前             | 环境与上线可行性   | 是       |
| 备份恢复演练 | 上线前                 | 数据安全与恢复能力 | 是       |

## 11. 风险清单与应对

| 风险 | 描述 | 应对策略 |
| --- | --- | --- |
| 误删运行链路 | 将模板残留误判为核心依赖 | 先盘点调用关系，再改动，并用冒烟+集成回归验证 |
| 目录调整引发大面积引用失效 | 重构涉及路径和导出变更 | 分阶段迁移，保持每步可编译、可测试 |
| 权限边界回退 | 前端/后端职责调整后漏校验 | 强制补权限与隔离测试 |
| 上传链路受损 | 资产与 AI 附件共用对象存储流程 | 对预签名、完成登记、预览、下载建立回归清单 |
| 提交不可追溯 | 提交过大或混合多个目标 | 严格拆分 commit，并同步维护 commitlog |
| 重构中顺手扩需求 | 任务边界被不断放大 | 所有新增需求单独确认，不混入本轮 |
| 上线材料不完整 | 只完成代码，未完成交付证据 | 同步维护测试记录、文档和发布清单 |
