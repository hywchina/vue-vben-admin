- 输入分支：`dev`
- 目标分支：`refactor-core-module`
- 原始基线提交：`0c352a574`（`chore: capture core refactor baseline`）

- 领域主线：项目上下文 -> 资产契约 -> 应用能力 -> 任务链路 -> AI/外部能力边界

## 3. 保留、隔离与观察决策

| 分类 | 路径或能力 | 决策 |
| --- | --- | --- |

## 4. 当前结构问题

1. 前端平台 API 集中在单一入口文件，项目、资产、任务、权限、审计和通知边界不明显。
2. 前端平台类型集中在单一类型文件，跨领域引用范围过宽。
3. 平台 Store 同时承担项目上下文、资产、任务和管理数据协调，缺少可独立测试的状态辅助层。
4. 后端领域、身份、HTTP 和基础设施工具平铺在 `utils`，新成员难以快速定位职责。
5. 外部任务能力目前只通过数据库配置判断，缺少显式、可复用的能力适配器类型边界。
6. 静态样例文件虽未进入当前 Store，仍位于平台领域目录，容易被误用为运行时数据源。

## 5. 分阶段改造清单

1. 将前端 API 和领域类型按项目、资产、应用、任务、访问控制、审计通知、AI 助手拆分，并保留统一导出入口。
2. 抽取平台 Store 的任务显示转换和项目数据提交保护逻辑，保持 Store 公共接口不变。
3. 将后端共享工具按 `domain`、`identity`、`infrastructure`、`http` 分层，并更新显式引用。
4. 建立任务能力适配器公共契约，但不接入任何新外部服务、不改变任务创建行为。
5. 删除确认无引用的静态平台样例数据，测试证明运行态只依赖真实 API。
6. 更新测试、架构、质量门禁、开发记录、部署/运维核查和发布前清单。

## 6. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 路径迁移造成引用失效 | 每个领域保留稳定 barrel export；先改引用再删除旧路径；执行类型检查和构建 |
| Store 并发切换项目时串写 | 保留现有 projectId 快照比较，并补状态测试 |
| 权限或项目范围退化 | 不移动安全判断到前端；保留后端 `requirePermission`、`requireProjectAccess` 并运行集成测试 |
| 上传和附件链路受损 | 保留预签名 URL、完成登记、对象归属与错误码；运行资产和 AI 附件集成用例 |
| 外部能力伪成功 | 适配器边界保留 `ADAPTER_NOT_CONFIGURED`，不增加模拟输出 |
| 误删模板依赖 | 仅删除经全仓引用检查确认未使用的静态平台样例；模板页面继续隔离观察 |
